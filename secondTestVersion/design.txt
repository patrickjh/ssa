second test version

This folder is a design for a second trial. The programs
in the repo root and in testVersion stay as they are.
Nothing here runs yet.

Gemma 4 E2B and Gemma 4 E4B are the models this shape
is for. They struggle with a multi-turn agent. The test
version still asks the model to be the agent: emit a
pure script, call ssa-edit and ssa-ask with exact
heredocs, and decide when to write # complete. This
version does not do multi-turn ideas. The model
writes one script from one prompt. The job is help
remembering the syntax of how to do something.
Prompt in, script out.


A separate program

Keep this as its own program. Leave ssa and the test
version on their own prompts. Those prompts describe
an agent loop, reply markers, and tool blurbs. This
version exists so a small model never sees that
protocol.

The program is named ssa. Put this folder on PATH
to choose it, the same way as the test version.
-v, -y, and -m come before the task. -m is the
GGUF path. -y skips the question and runs the
script.

-v is in the first version so it can be tried.
The hope is that -v shows all of the llama-cli
output on stderr. That may not be feasible. The
echo, the timings, color, and the reasoning
trace share a stream with the script. How -v
should work, and whether this version should
have -v at all, waits on that try.

Leave these out:

- curl, jq, and llama-server
- the port and the cloud probe
- the agent loop
- # complete
- ssa-edit and ssa-ask
- dropping old turns to fit a budget
- a long-running llama-cli conversation
- a feedback turn, or a fix from the script output
- sending the old script in the next call
- a JSON log
- a file created by this program
- $EDITOR
- editing or appending the prompt inside the program


llama-cli, one turn

The model call is llama-cli in single-turn mode. Pass
-st and a system prompt. Do not pass --prompt. The
system text ends with the task. llama-cli applies
the chat template, writes one reply, and exits.

This program's standard input is llama-cli's
standard input. A pipe is the user turn. There is
no "No context was given on stdin." line. When
standard input is a terminal, end llama-cli's
standard input at once. It gets no user turn, and
it does not wait at the > prompt.

This is a local program. It does not speak HTTP.

Each run starts llama-cli once, which loads the
GGUF. There is no assistant history. The old
multi-turn llama-cli setup stays out.

The reply has to be the script alone. A piped turn
is echoed, often as a > line, and the reply can
end with [end of text]. Those are not part of the
script. The echoed turn, the timings, color, and
the reasoning trace share stdout with the reply.
The question shows the script alone. -v tries to
show the whole llama-cli output on stderr as
well. Whether that split can be done is part of
the try.

The caller cannot change llama-cli settings. The
program picks the flags. Context size, GPU layers,
and sampling stay at llama-cli defaults. The
program does not read stdin, so it does not cap
it or refuse it. llama-cli's own context size is
the limit.

Gemma templates often have no system role. llama-cli
then places the system text at the start of the user
turn. The model still sees the instructions and the
task first, then the context. That is the same merge
the chat template uses for those models on
llama-server.


One call, one script

Each model call is a system message plus, when
stdin is a pipe, one user message. The system
message holds the instructions and the task. The
user message is that pipe. It does not include an
earlier script, a run's output, or a change line.
A terminal on stdin adds no user message.

The task is the task words on the command line.
The program does not keep the task, and it does
not change it. To try different words, the person
edits the command in the shell and runs it again.
That run is a new first turn.

The reply is one script, kept in a shell variable.
These models can write a short script from a
description of the job. A search/replace block,
which is what ssa-edit requires, stays out.


The system text

The system text stays short. The task is the last
part of it:

You write one POSIX sh script. Reply with the script
only. Put reasoning in # comments. No markdown fences.
If the task is ambiguous, pick the usual form and
name the assumption in a comment.

The task for this run:
find files bigger than 100M

A comment is the stand-in for a question. A question
would be a second turn and another format to obey.


The menu

The menu never goes to the model. The reply stays
in a shell variable. It is shown on the terminal,
then the program asks:

run this script?

Yes. Run the variable with sh -c, so the script
keeps the terminal as its standard input. Then
the program exits.

No. Do not run the script. The program exits.

-y skips that question. The script runs, as with
Yes.

The shell keeps the command line. Pressing up
puts that line back so the person can edit it
and run the program again. The program does not
edit or append the prompt. History stores the
command line, not text that arrived on standard
input. A pipeline has to be part of the command
if it should come back with that line.

The program creates no files. The script stays
in a shell variable for this run. llama-cli
still reads the GGUF that is already on disk.
cd stays outside the program.


Small model failures

When the reply has a markdown fence, the script is
the text inside that fence. Show that text, and
Yes runs it. A fence may name a language. That
name is not part of the script.

Do not send the reply back for a format error.
That would be a second turn. These models often
answer it with an apology and another fence.

When the reply has no fence, show the reply. The
person can answer No, edit the command in the
shell, and run the program again.

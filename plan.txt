5) Figure out how to turn reasoning on

Reasoning is off. ssa passes --reasoning off and
--reasoning-budget 0. AGENTS.md says not to add a
thinking trace the device must generate, and it
lists thinking left on, with the trace stripped
from history, as kept out.

Work out a later change that turns reasoning on
and still reads one action per reply. Do not
change ssa, README.md, or AGENTS.md for this task.
When the approach is clear, add it here as the
next task.

The reply and the trace share one stdout. On
current llama-cli the trace is a prefix, marked
by the lines [Start thinking] and [End thinking].
The reader stops at the first line that is exactly
# end. The first action line in that text is the
action. A trace that contains an action line or
# end is taken as the reply.

ssa does not send the model reply back. llama-cli
keeps the chat, so a trace stays in later turns
unless a llama-cli flag drops it. Context shift
drops old turns and keeps the system prompt.

The system prompt tells the model to put reasoning
in # comments and to use no thinking tags. Any
approach has to say what that text becomes.

Say what happens to the low-token goal and the
kept-out line. Leave both as they are until that
decision is written down.

6) Ring the terminal when an ask is waiting

When ssa waits for an answer, write the terminal
bell (BEL) to /dev/tty. POSIX printf '\a' is the
chime. Do not send it through sanitize_output.
That path turns BEL into ?.

Ring once before the loop that asks whether to
apply the action, so a bad answer does not ring
again. Ring again before the read that asks for
a rejection reason. SSA_NO_ASK=1 never reaches
those reads, so that path stays quiet.

Add no SSA_* setting. Muting the bell is a
terminal option. Add one sentence to the loop
section of README.md so a silent terminal is
not mistaken for a hang. Whether a sound plays
depends on that terminal.

7) Add a # question reply

A question reply matches a script: one action
line, a body, then # end.

# reasoning: the path was not in the task
# question
Which file should I edit?
# end

The lines between # question and # end are the
question. An empty body is a format error, the
same as an empty script. first_action_line gains
question$ so this line is recognized.

There is no yes or no prompt. Show the question
on /dev/tty and read one line. A blank line is
still an answer. Interrupt is how the user
quits. Ring the bell on this wait too, once
that task is in ssa.

The answer is the next user message. Log it as
its own # sent to model chunk, as the answer
text, with no action exit code. The following
call already sends the latest chunk.

SSA_NO_ASK=1 has no user to answer. # question
is a format error in that run, and the error
goes back to the model like a disallowed write.
Add no SSA_* setting. Leave the startup check
that stops a run when scripts, writes, and
edits are all off.

Add a short question spec beside the other
reply specs. List this shape in the loop
paragraph of README.md.

8) Add a # response reply

A response reply is the text outcome of the
task. The user reads it, and the run ends. The
shape matches a script: one action line, a
body, then # end.

# reasoning: the test failure is in this file
# response
ssa
# end

The lines between # response and # end are the
text. An empty body is a format error.
first_action_line gains response$. There is no
yes or no prompt, and no bell.

The run ends the same way # complete ends it,
with exit status 0. The body is the result, so
write it to the caller's stdout. SSA_VERBOSE=0
still shows it. start_llama points stdout at
/dev/null when SSA_VERBOSE=0. Keep a copy of
the caller's stdout before that redirect, and
write the body there. The load text and the live
reply stay on the progress stream. With
SSA_VERBOSE=1 the raw reply was already shown,
and the body is printed again as the result.

SSA_NO_ASK=1 does not block this. A response
changes no files. Add no setting. # complete
stays the ending for a task handled by a
script, a write, or an edit.

Add a short response spec beside the other
reply specs. List this shape in the loop
paragraph of README.md. Leave the startup check
that requires a script, a write, or an edit.

9) Put the documented llama-cli flags back

README.md lists five flags the harness does not
pass: --offline, --no-display-prompt,
--no-show-timings, -lm mmap, and -np 1. The
prefix in ssa has the rest of that list. The
caller's SSA_LLAMA_CLI_ARGS still follow the
prefix.

Add the five in the order README.md already
uses. --offline is the no-network goal. -lm
mmap is the goal that weights can be larger
than memory. --no-display-prompt is what the
comment in log_llama_output already assumes.
--no-show-timings keeps timing lines out of
the reply. -np 1 is already in the help; pass
it too.

Leave the > strip in first_action_line. A
prompt can still glue to the first line.
README.md already describes these flags, so
change it only if that list is then wrong.

10) Take text after # end into this reply

The reader stops at the first line that is
exactly # end. Text the model already wrote
after that line stays in the output fifo. The
next turn reads it first and treats it as part
of the new reply. An action line, a markdown
fence, or the tail of a cut file then lands in
the wrong chunk.

Before end_log_chunk, take that extra text
into this reply's log chunk, after the # end
line, and leave the fifo empty before the next
send. The reply slice must include it, so the
text-after-end check can see it.

Do not block. A blocking read past # end waits
forever. The comment in log_llama_output
already says so. read -t is not POSIX, so do
not use it. Read only what is already in the
fifo, without waiting. If that needs a tool
option that is not POSIX, document the
required behavior, as the POSIX task says. A
later turn must not see that text.

11) Make the text-after-end check able to match

reply_has_text_after_end scans the reply
slice. The slice ends on the # end line the
reader stopped at, so the check never matches.
The extra text shows up as the start of the
next reply instead.

Do this after the task that logs text after
# end in the same chunk. Blank lines after
# end stay allowed. The awk already skips
them. Any other text is the format error this
check already records. Keep the check.

12) Reject a body cut short by a marker line

A body cannot contain a line that is exactly
# end. The reader stops there. Once text after
that line is part of the same slice, the
text-after-end check runs before the action.
A cut write, edit, or script must not be
applied. Change the format error so it tells
the model that a body line must not be exactly
# end.

An edit has the same limit on its own markers.
A search or replace block cannot contain a
line that is exactly ======= or
>>>>>>> REPLACE. Those lines end the block
early. Fail that edit with a message that
names the limit. Do not write a shortened
file.

Say both limits in the reply specs the model
reads.

13) Stop after repeated format errors

A reply that fails the format checks is sent
back, and the loop continues. With
--context-shift and --keep -1 the context does
not fill, so a model that keeps failing never
stops.

Count format errors in a row inside
record_format_error. Any other reply resets
the count. After 5 in a row, die. Add no
SSA_* setting. The message should say the
reply format failed repeatedly.

14) Strip carriage returns from model lines

Do this in the reader, before the line is
logged and before it is compared to # end. A
line that is # end plus a carriage return must
count as # end. Leave the carriage return out
of the log and out of a script, write, or edit
body. One place only, so the slice, the end
check, and the action body all see the same
line.

15) Document lines a body cannot hold

In the loop section of README.md, state the
limits. A body must not contain a line that is
exactly # end. A search or replace block must
not contain a line that is exactly ======= or
>>>>>>> REPLACE. The reader and the edit awk
stop on those lines. Keep the paragraph short.

1) Ask several models for changes

Have more than one model read ssa and AGENTS.md.
Each model suggests changes that would improve the
project. Have them check AGENTS.md and POSIX
compliance. Have them review the system prompt.

Add those suggestions as tasks in plan.txt. Leave ssa
and AGENTS.md as they are while collecting them.

2) Strip the llama-cli prompt from the first line

llama-cli glues > or >  to the first line of a
reply. Only the action lookup strips it. The log,
the action body, the edit parser, and the # end
check use the raw line.

If that first line is the action, a write saves an
empty body and truncates the file. A script, a
question, or a message looks empty. An edit fails
its format check. If that first line is # end, the
run never sees the end line and waits forever.

The preferred solution is that the log is an
accurate record of what actually happened. Leave
the glued > on the logged line. Strip one leading
> and one optional space from a copy of the first
line before that copy is shown or compared to
# end. Leave later lines as they are.

3) Finish the log after the main process exits

# llama-cli stderr is written by watch_llama. The
main process writes # run end and exits without
waiting, on a normal finish, on die, and on
hangup, interrupt, and terminate. The stderr block
lands after # run end, and often after ssa has
returned. die and the signal traps also remove the
pipe directory while watch_llama still reads it.

Have watch_llama wait until the main process
exits, then append # llama-cli stderr and then
# run end. The main process records the status,
then exits. It does not write # run end, and it
does not remove the pipes. watch_llama removes
them after the log tail is written. The main
process must not wait on watch_llama, or the two
wait on each other.

If llama-cli was never started, there is no
watch_llama. The main process writes # run end
itself, as it does now.

The log still ends with # run end. README already
says that. Change README only if this makes a
sentence wrong.

4) Reject a bad edit before the ask

Missing search, middle, or replace markers, and
text after the replace marker, are found only
after the user approves the edit. Repeated
======= and >>>>>>> REPLACE lines are already
rejected before the ask.

Reject those format errors before the approval
prompt. Send them back as format errors. Do not
ask the user to apply an edit that will fail as
a bad format.

5) Keep the caller's llama-cli args in the environment

The harness prepends its flags to
SSA_LLAMA_CLI_ARGS. A script inherits that value.
A nested ssa prepends the same flags again.

Leave the caller's value in the variable. Pass
the harness flags and the caller's flags to
llama-cli at the exec. The log still records the
caller's SSA_LLAMA_CLI_ARGS and the flags that
were passed.

6) Say how to fix a missing tool

AGENTS.md says a missing tool on PATH should
tell the user to install it or put it on PATH.
The checks die with "not found on PATH" and
"llama-cli or llama not found on PATH". Neither
says that.

Name the tool. Say to install it or put it on
PATH. One short clause. Do not add a "set ENV"
hint. A missing tool is not a setting.

7) Spell out short names

AGENTS.md forbids abbreviations. argument, not
arg. command, not cmd. Tool names stay as they
are: llama-cli, head, sed.

These names are short forms:

- ERR, the edit failure text
- FIFO_DIR, the pipe directory
- mid_lines, the middle marker count
- SSA_LLAMA_CLI_ARGS and check_llama_cli_args

Use the full word. ERR becomes ERROR. FIFO_DIR
becomes PIPE_DIRECTORY. mid_lines becomes
middle_lines. The setting
becomes SSA_LLAMA_CLI_ARGUMENTS, and the check
becomes check_llama_cli_arguments. ARGS is the
short form. llama-cli stays llama-cli, because
that is the tool name.

The setting is user-facing. Put the new name in
README. The log line that prints it changes
with the name.

8) Use if for an early return

AGENTS.md says prefer if over a test and a
command when the branch chooses an action. A
guard that returns is an if, with the return
inside.

The tty check returns with && return when
/dev/tty opens. The write handler returns with
|| return when the user says no. The edit and
the script handlers already use elif for that
ask.

Write both as if blocks. The tty check returns
from inside the if. The write handler returns
from inside the if when the ask fails. Same
behavior.

9) Do not keep the write path as run state

AGENTS.md says a value used in one place is
written there. Keep a variable when the same
fact is read again later. The exit code is
already passed straight through.

FILE_TO_WRITE is run state. The write handler
sets it. The apply function reads it twice:
the redirect, and the wrote-file line. Nothing
else reads it.

Drop it from run state. Take the path in the
function that writes the file. A local there is
fine, because that function reads the path
twice.

10) One setting for what a run may do

Six settings each turn one thing off. They are
SSA_NO_ASK, SSA_NO_EDITS, SSA_NO_MESSAGES,
SSA_NO_QUESTIONS, SSA_NO_SCRIPTS, and
SSA_NO_WRITES. Each must be 0 or 1. Each has
its own check. The log prints all six. The
system prompt adds a reply spec for each
action that is still on. The run stops when
scripts, writes, edits, questions, and
messages are all off.

SSA_NO_ASK is not an action. It skips the
ask before a script, a write, or an edit.
With no /dev/tty, it also turns questions
and messages off.

Maybe one setting, SSA_ALLOWED_ACTIONS, can
stand in for the six. A bit map is one
shape: one bit for a script, a write, an
edit, a question, a message, and the ask.
Unset means what the six defaults mean now:
those actions on, and the ask on. # complete
is not a bit. It still does not keep a run
going by itself.

POSIX sh has no bit test. A string of names,
or a string of bits, both work. Pick a shape
a person can set in the environment.

The log and README record that one setting.
Drop the six SSA_NO_* names. A bad value
names SSA_ALLOWED_ACTIONS. No /dev/tty still
needs the ask off, and still turns questions
and messages off. No action left still stops
the run.

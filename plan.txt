1) Ask several models for changes

Have more than one model read ssa and AGENTS.md.
Each model suggests changes that would improve the
project. Have them check AGENTS.md and POSIX
compliance. Have them review the system prompt.

Add those suggestions as tasks in plan.txt. Leave ssa
and AGENTS.md as they are.

2) Log llama-cli errors

watch_llama sends llama-cli stderr to the
stdout this process inherited. With
SSA_VERBOSE=0 that text is dropped. With
SSA_VERBOSE=1 it is printed and not stored.

A load failure then dies with "llama-cli
exited", and the useful text is gone. The
full log needs that text.

Write llama-cli stderr into the log.
SSA_VERBOSE=0 still hides it from the screen.
SSA_VERBOSE=1 can still print it. Update
README.md only if a person would otherwise
not know where that text goes.

3) Record the run in the log

The log does not record the llama-cli version,
the effective arguments, the working directory,
the runtime settings, the start time, the end
time, or the final status. A later read of the
log cannot rebuild the run.

Write the start of the run before the system
prompt. Use llama-cli --version, or llama cli
--version when that is the command ssa runs.
Record the working directory, each SSA_* value
in effect after the startup checks, the flags
ssa passes, and the start time. Use the same
date form as the log file name. The system
prompt is already its own chunk, so do not copy
it again.

When the run ends, record the end time and the
final status. A completed task says it
completed. A die says so and includes the die
text. A hangup, interrupt, or terminate says
which signal ended the run.

Add no SSA_* setting. Update README.md only if
a person would otherwise not know what the log
starts and ends with.

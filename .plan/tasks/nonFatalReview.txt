nonFatalReview — a failed review POST is a warning, not a run failure

Why:
review_work (ssa:814-824) always runs one more model POST after the
loop, and a failed curl there is fatal (exit 1) even when the task
itself completed (exit 0). That nonessential call adds latency and
cost to every run and lets a flaky provider or network turn a
success into a failure. AGENTS.md:145-149 and the test
tests/reviewWork/missingReviewReplyIsFatal.test.sh lock this in.
Review is a nicety, not part of the task.

Do:
On a failed review curl, print a short warning on stderr (for
example "review skipped: curl failed") and do not exit. The run
keeps the exit status the loop produced (0 for done, 1 for hit
max). Do not run the model reply (there is none). Keep the
review POST itself; only downgrade the failure. Do not add a
setting to disable review (callers who want no review can point
SSA_URL at a stub, or a later task can add SSA_NO_REVIEW if
needed; not this job).

Update AGENTS.md Review (ssa:145-149): a failed review curl is a
warning, not fatal; the run keeps its loop exit status. Update
HELP_TEXT (ssa:89) only if the one-line review mention implies
fatality (it does not name it; leave -h alone).

Size:
About 3-6 lines in ssa (wrap the call_curl in review_work, or
catch the die). AGENTS.md one sentence. -h unchanged.

Tests:
Update tests/reviewWork/missingReviewReplyIsFatal.test.sh to
expect exit 0 (the task completed) and a stderr warning, not
exit 1 and "curl failed". Rename the file or keep the name with
a new comment (preferred: rename to missingReviewReplyIsWarning
or reviewCurlFailureIsNonFatal). Add or keep a case that a
successful task with a failed review still exits 0 and prints
the done line. Fake curl, SSA_NO_ASK=1, SSA_TEST_NO_REVIEW_REPLY=1.
